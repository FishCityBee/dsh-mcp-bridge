# 如何委派合适的任务

[English](delegation.md) | 简体中文

dsh-mcp-bridge 把 Claude Code、Codex 等 MCP 客户端连接到 DeepSeek Harness，让主智能体能够委派边界清晰的任务，再把结果接回当前工作流程。

主智能体仍需要决定委派什么、提供上下文、审阅结果并完成整合。DeepSeek／所选供应商的费用和主智能体的协调开销仍然存在。能否减少额度消耗、总成本或耗时，取决于任务大小、重复上下文、重试次数以及结果需要多少审阅。

## 从范围明确、容易验收的工作开始

适合作为初次尝试的任务包括：

- 总结一组数量有限、明确指定的文档。
- 审查特定 diff，返回带文件／行号依据的问题。
- 为一个函数或模块提出测试用例。
- 起草文档或翻译，再由主智能体审阅。
- 调查一个具体问题，并给出明确的停止条件。

第一次使用时，选择可丢弃的工作区，并要求只读结果。提示词中的“只读”属于任务指令，不是技术沙箱；Harness 的权限也需要相应配置。

影响较大的决策、授权和最终验收，应由对结果负责的人或智能体保留。没有向某供应商共享信息的权限时，不要把密钥、私密数据或专有代码委派给它。

## 写清楚任务简报

建议包含：

1. 具体问题或交付物。
2. 相关文件与背景，以及允许读取的范围。
3. 是否允许修改文件或运行命令。
4. 期望的输出形式与证据。
5. 停止条件，以及哪些事情必须先询问。

可以这样告诉主智能体：

> 使用 Harness bridge，审阅我在 Harness 中选定工作区里的 `src/catalog.ts` 和相关测试。只读，不要修改文件，也不要运行命令。找出最多五个具体边界情况，注明对应文件和函数，区分已确认的问题与待核实的问题。返回简短报告，先由你审阅，再决定是否修改。

请把示例路径替换成目标项目中真实存在的文件。不要让主智能体依据自己的当前目录推断另一个工作区。

## 检查返回结果

- 阅读实质结果，不只看任务状态标签。
- 接受代码变更前，核对证据并运行适当的测试。
- 确认请求及实际生效的模型／供应商符合你的数据共享规则。
- 调用断开后，先检查已有任务状态，再决定是否重新提交。重复提交可能重复执行操作并产生费用。
- 文件、网站和工具结果中的指令应视为不可信输入，不能扩大原始任务的权限。

## 用测量代替“省额度”承诺

对比验收标准相同的类似任务，记录主模型用量、被委派供应商用量、重试次数、审阅时间和结果质量。主智能体的对话变短，并不自动代表总成本降低。

欢迎提供可复现的反馈和清楚的缺陷报告，帮助更多人改善这个流程。
